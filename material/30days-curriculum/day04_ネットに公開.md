# Day 04: ネットに公開

Day 01 で土台を立ち上げ、Day 02 でダッシュボードに自分の情報を表示し、Day 03 で GitHub に保存しました。

今日は、このアプリを Vercel（作ったアプリをインターネット上に公開できるホスティングサービスです。読み方: ヴァーセル）を使ってインターネット上に公開します。公開して URL が発行されると、自分のパソコン以外からもアプリを開けるようになります。スマホやほかの人のブラウザからもアクセスでき、いま作っているものを実際に見せられる状態になります。

Phase 1（環境構築・即公開）の最終日は、新しい機能を追加する日ではありません。すでに作ったアプリを、誰でもアクセスできる状態にすることが今日のゴールです。Vercel での公開手順を、順を追って進めます。


## なぜこれを作るのか

ここまでのアプリは `http://localhost:3000` でしか開けません。`localhost` は「このパソコン自身」を指す名前なので、同じ URL を人に送っても相手の画面には自分のアプリは出てきません。相手のパソコンの中を見に行ってしまうためです。

外から届くようにするには、自分のパソコン以外の場所にアプリを置く必要があります。それが今日やるデプロイです。Vercel を使うと、GitHub にあるコードを取ってきて、ビルドして、URL を1つ発行するところまでを自動でやってくれます。

そしてもう1つ、今日ここで公開しておく理由があります。**残りの26日ぶん、作った機能をその日のうちに人へ見せられるようになる**からです。30日目にまとめて公開する形だと、途中で詰まったときに「そもそも公開できるのか」という不安まで抱えることになります。先に道を通しておけば、あとは中身を育てるだけで済みます。

> **例え話**: `localhost` は自分の部屋の机です。デプロイは、その机の上のものを店先のショーケースへ移す作業にあたります。中身は同じでも、置く場所が変われば通りすがりの人にも見えます。

### 新しく学ぶ概念

| 概念 | 読み方 | 役割 | 例え |
|------|--------|------|------|
| Vercel | ヴァーセル | Next.js アプリを手軽に公開できるホスティングサービス | レンタルキッチン。作った料理をお客さんに出せる場所 |
| デプロイ | — | アプリをサーバーに配置して公開する操作 | 料理をお店のテーブルに出すこと |
| ビルド | — | ソースコードを本番用の形に変換する処理。`npm run build` で走る | 仕込みの総仕上げ。お客さんに出せる状態にする |
| 環境変数 | かんきょうへんすう | 接続先やパスワードを、コードの外から渡す仕組み | レシピに直接書かず、店の金庫に入れておく秘密の材料 |
| 接続文字列 | せつぞくもじれつ | データベースの場所とログイン情報を1本にまとめた文字列。`DATABASE_URL` に入れる | 住所と鍵をひとまとめにしたメモ |

### Step 1: GitHub 側の完成状態をもう一度確認する（3分）

Vercel に持っていく前に、まずは Day 03 の終点が揃っているかを確認します。

デプロイの失敗は、Vercel だけが原因とは限りません。GitHub 側に送りきれていない、見たいブランチに変更が入っていないなど、出発点のズレで止まることも多いです。そのため、まずは公開前の現在地を確認します。

#### 実行コマンド

```bash
pwd
git status -sb
git branch --show-current
git remote -v
git log --oneline --decorate -3
```

この5つは、どれも状態を読むだけのコマンドです。ファイルやコミットを書き換えないので、途中でやめても手元は壊れません。確かめたいのは1点だけです。Vercel はこのあと手元のパソコンではなく GitHub を読みに行くため、両者の中身がそろっている必要があります。ここがずれたまま進むと、直したはずの表示が公開後も古いまま残ります。しかも原因を Vercel の設定側で探すことになり、初回公開でいちばん迷う形になります。

#### ここで見たいこと

- `pwd` が `task-app` のルートを指している
- `git status -sb` で大きな未保存差分が残っていない
- `git branch --show-current` が `main` になっている
- `git remote -v` で GitHub の `origin` が見えている
- `git log --oneline --decorate -3` に Day 03 までの履歴がある

#### GitHub のブラウザ画面でも確認する

ターミナルでの確認だけで終わらせず、GitHub のリポジトリページもブラウザで開きます。ここで次が見えていれば問題ありません。

- `README.md` が表示されている
- `src` ディレクトリがある
- `src/app/dashboard/page.tsx` が存在する
- 一番上に表示されているブランチが `main` になっている

GitHub 側で見えているものが、今日 Vercel が読み込む対象になります。

### Step 2: 公開前にローカルで `npm run build` を通す（5分）

ここは今日の大事な一手です。

Vercel が build してくれるので先にプッシュしてから確認すればよい、と思いがちですが、この進め方はあとで手間が増えやすいです。

Vercel の失敗ログも確認できますが、まずローカルで `npm run build` が通るかを確認しておくと、公開前にエラーを切り分けやすくなります。公開前にローカルで一度ビルドを通す習慣をつけておきます。

#### 実行コマンド

```bash
npm run build
```

このコマンドは、Day 01 から使ってきた `npm run dev` とは別の道を通ります。`dev` は書き換えるたびに画面へ反映する速さを優先するので、型のずれが少し残っていても、そのページを開くまでは動き続けます。`build` は本番用の完成品を1回だけ作る処理で、途中で全ファイルの型をまとめて確認します。だから、まだ開いていないページに残った型のずれもここで止まります。そして Vercel が公開のときに走らせるのも、この同じ `build` です。手元で通ることを先に確かめておけば、Vercel で同じ場所につまずく可能性をあらかじめ減らせます。

`build` が見てくれるのは型までです。使っていない変数が残っていても、型としては正しいので `build` は止まりません。そちらを見つけるのは `npm run lint` の役目なので、消し忘れが気になったら別で走らせてください。

#### 期待する結果

環境差はあるけど、
だいたい次のような流れになればよいです。

なお `npm run build` は、その中で `prisma generate` も実行します。
そのため `▲ Next.js` の行より先に Prisma の行が数行流れます。
`Generated Prisma Client` という行が出ていれば、そこは正常です。
ページ数の `(6/6)` の部分は、その時点のページ数によって変わります。ここまでの3日ぶんを素直に進めた状態なら、この数字になります。

```text
   ▲ Next.js 15.5.21
   - Environments: .env

   Creating an optimized production build ...
 ✓ Compiled successfully in 13.2s
   Linting and checking validity of types ...
   Collecting page data ...
 ✓ Generating static pages (6/6)
   Finalizing page optimization ...
   Collecting build traces ...
```

最後まで止まらず完走すれば、
今日の公開にかなり自信を持って進めます。

この行が順に流れるのは、build が決まった順番で進むからです。ページ数や秒数は手元の状態で変わります。ソースの変換、型の確認、ページごとの下ごしらえ、最後に最適化、という並びになっています。だから途中で止まったときは、最後に出た行の名前がそのまま調べる場所を教えてくれます。`Linting and checking validity of types` の行で止まれば、まず型の書き間違いを疑います。`Generating static pages` まで進んでいたなら、型ではなくページ側の処理でエラーが起きています。

#### もしここで止まったら

落ち着いて、
まずローカルの build エラーを直しましょう。

赤い文字がたくさん出ても、全部を読む必要はありません。見るのは次の3つです。

- 最初に出た赤い行。あとに続くエラーは、その巻き添えで出ていることが多い
- `Error:` や `Type error:` のあとに書かれている内容
- `./src/...` のようなファイル名と、その横に付いている行番号

なぜ最初の1行を優先するかというと、build は途中で1か所つまずくと、その先の処理も連鎖で止まるからです。だから下の方のエラーを追いかけるより、一番上のエラーを直す方が早いです。ファイル名と行番号が分かれば、直す場所は「どのファイルの何行目か」まで絞れます。まずはそのファイルのその行を開いて、直前に自分が変えたところと見比べます。多くは書き間違いや消し忘れが原因です。

この時点なら、
Vercel の設定が悪いのか、
コード自体が build できていないのか、
原因の切り分けがとてもやりやすいです。

逆にここを飛ばすと、
Vercel 側の UI とログを見ながら原因を探すことになって、
初回公開ではかなり迷いやすいです。

今日は最速でボタンを押す練習ではなくて、
**公開までの流れを自分で再現できるようになる**
のが狙いです。

### Step 4: GitHub の `task-app` リポジトリを Import する（5分）

ログインできたら、
Vercel に Day 03 で作った GitHub リポジトリを読み込ませます。

ここで選ぶのは、
**自分の `task-app`** です。

#### 進め方

1. Vercel のダッシュボードで `Add New...` を押す
2. `Project` を選ぶ
3. GitHub リポジトリ一覧から `task-app` を探す
4. 見つかったら `Import` を押す

#### リポジトリが見つからないとき

だいたい次のどちらかです。

- GitHub 連携の権限がまだ足りていない
- Vercel にリポジトリアクセスを許可していない

この場合は、リポジトリ一覧の近くにある `Adjust GitHub App Permissions`（環境によっては `Configure GitHub App`）を押します。GitHub の設定画面が開きます。`Repository access` の項目で `All repositories` を選ぶか、`Only select repositories` から `task-app` を選んで保存します。Vercel の画面に戻ると、一覧に `task-app` が出てきます。

ここでコードを直す必要はありません。Vercel から見えないのは、多くの場合「どのリポジトリを見てよいか」という許可がまだ渡っていないだけだからです。直す場所も、コードではなく GitHub 連携の許可範囲になります。

初回でここに数分かかるのは普通です。
焦らなくてよいです。

#### Environment Variables には2つだけ設定する

Day 04 のスコープは、
**まず自分のアプリを公開 URL で見られるようにする**
ところです。

ただし、`DATABASE_URL` と `JWT_SECRET` の2つは今日必要です。
配布コードは起動時に環境変数を検証する作りになっていて、
`DATABASE_URL`（有効な URL 形式）と `JWT_SECRET`（32文字以上）が
無いとエラーを出して止まります。
Vercel 上でも同じ検証が走るため、
空のままではデプロイしたアプリが起動しません。

新語の表で「環境変数＝店の裏の金庫」と例えました。今日はその金庫に、鍵を2本だけ入れます。それ以外の値は、本番公開を仕上げる Day 30 で扱います。

```mermaid
flowchart TB
    ENV[".env<br/>手元の本物の値<br/>GitHub へは送らない"]
    EX[".env.example<br/>名前だけの見本<br/>GitHub へ送る"]
    VER["Vercel の Environment Variables<br/>公開版の本物の値"]
    NEON[("Neon の PostgreSQL")]
    ENV -.->|"名前だけ写す"| EX

```

同じ名前の設定値が3か所に分かれて置かれます。本物の値が入るのは `.env` と Vercel の2か所だけで、GitHub に載るのは名前だけの見本です。実線は値が実際に使われる向き、点線は名前をそろえる作業を表します。

#### JWT_SECRET を用意する

手元のターミナルで、次のコマンドを実行します。

**ターミナル（どこでもOK）**

```bash
openssl rand -base64 48
```

長いランダムな文字列が1行表示されます。
これが JWT（ログイン状態の証明に使う署名付きデータ）の
署名用シークレットになります。
表示された文字列をコピーして、Environment Variables の欄に
Key を `JWT_SECRET`、Value をその文字列として追加します。

#### DATABASE_URL を用意する

Vercel から接続できる PostgreSQL が1つ必要です。
無料枠のあるサービスに [Neon](https://neon.tech) や
[Supabase](https://supabase.com)（PostgreSQL を無料枠から使えるクラウドサービス）があります。
どちらかでアカウントを作ってデータベースを1つ作成すると、
`postgresql://` で始まる接続文字列
（ホスト名やパスワードをまとめた1行の接続情報）が発行されます。
それを Key `DATABASE_URL` の Value として追加します。

ここでは Neon を例に、実際の手順を書きます。

1. `https://neon.tech` を開き、`Sign up` から GitHub アカウントで登録する
2. 登録後の画面で `Create project` を押す
3. プロジェクト名はそのままでよいので、`Create` を押す
4. 作成直後に出る `Connection string` の欄で、`postgresql://` で始まる1行をコピーする
   （欄が見当たらないときは、左メニューの `Dashboard` から `Connect` を押す）
5. コピーした1行を、Vercel の Environment Variables に Key `DATABASE_URL` として追加する

画面の見た目はサービスの更新で変わります。ボタンの名前が違っていても、
やることは「プロジェクトを作る」「接続文字列をコピーする」の2つだけです。
Supabase を使う場合も、この2つに当たる操作を探してください。

本番データベースの本格的な運用（テーブル作成やデータ投入）は、
後日の Day で扱います。
今日は「起動時の検証を通すための接続先」が1つあれば十分です。

## つまずきポイント

| エラー / 問題 | 原因 | 解決方法 |
|--------------|------|---------|
| `npm run build` が `Type error:` で止まる | 型の書き間違いが、開いていないページに残っていた。`npm run dev` は開いたページしか確認しないので気付けない | 赤い行のうち**いちばん上**だけを読む。`Type error:` の後ろに理由、その下にファイル名と行番号が出る。そこを直して `npm run build` をやり直す |
| ページ数が教材の `(6/6)` と違う | 作ったページの数はその時点の状態で変わる | 数字は合っていなくてよい。`Collecting build traces` まで止まらずに進んでいれば成功 |
| Vercel の Import 画面に `task-app` が出てこない | Vercel の GitHub App に、そのリポジトリを見る権限を渡していない | `Adjust GitHub App Permissions` から `task-app` を選んで許可する。Private リポジトリの場合は特に起きやすい |
| Vercel の Deploy がビルドエラーで止まる | 手元で通っていないコードを送っている、または環境変数が足りない | まず Step 2 の `npm run build` が手元で通るか確かめる。通るなら、Environment Variables に `DATABASE_URL` と `JWT_SECRET` が入っているかを見る |
| 公開 URL の画面が、手元で直したはずの内容になっていない | GitHub へ push していない。Vercel はコードを手元ではなく GitHub から取りに行く | `git status` で未コミットの差分を確かめ、`git add` → `git commit` → `git push` まで進めてから、もう一度 Deploy する |
| 公開先だけビルドの結果が手元と違う | Node のバージョンが手元と公開先でそろっていない | Day 03 の Step 7 で `.node-version` を add したか確認する。送っていなければ add して push し直す |
| 公開 URL をスマホで開くと表示が崩れる | 画面幅の狭いときの指定が入っていない | 今日は直さなくてよい。崩れた場所をメモしておいて、以降の Day でレイアウトを作るときに直す |
| `DATABASE_URL` を GitHub に置いてしまった | 本物の値と見本の区別が付いていない | 本物は Vercel の Environment Variables にだけ置く。GitHub には `.env.example` の見本だけを送る。すでに送っていたら、Day 03 の Step 10 の手順で鍵を作り直す |

## 今日学んだ用語

| 用語 | 意味 |
|------|------|
| Vercel | Next.js アプリを GitHub から取ってきて公開してくれるホスティングサービス |
| デプロイ | アプリを公開用のサーバーに置いて、誰でも開ける状態にすること |
| ビルド | ソースコードを本番用の形に変換する処理。`npm run build` で走る |
| Production Deploy | 本番用として公開する Vercel の操作。ここで発行された URL が人へ送る URL になる |
| 環境変数 | 接続先やパスワードを、コードの外から渡す仕組み |
| 接続文字列 | データベースの場所とログイン情報を1本にまとめた文字列 |
| Neon | ブラウザだけで PostgreSQL を1つ用意できるサービス。今日は公開先から使う DB として使う |
| シークレットウィンドウ | ログイン状態やキャッシュを持たない状態でページを開くブラウザの機能 |

## 理解チェック

今日の作業を思い出しながら答えてみてください。答えは各問のすぐ下にあります。

**Q1. `npm run build` は `npm run dev` と何が違いますか。**

A. 確認する範囲が違います。`dev` は書き換えるたびに表示を作り直すので、開いていないページに残った型のずれは見つかりません。`build` は本番用の完成品を1回だけ作り、その途中で全ファイルの型をまとめて確認します。Vercel が公開時に走らせるのも、この `build` と同じ処理です。だから公開前に手元で通しておくと、失敗する場所を先に見つけられます。

**Q2. 手元のコードを直したあと、GitHub へ push せずに Vercel で再デプロイすると、公開 URL はどうなりますか。**

A. 直す前の内容のままです。Vercel がコードを取りに行く先は自分のパソコンではなく GitHub なので、push していない変更は公開されたアプリに出てきません。「公開先だけ古い」と感じたときは、まず `git status` で送り忘れを疑ってください。

**Q3. `DATABASE_URL` と `JWT_SECRET` を、GitHub ではなく Vercel の Environment Variables に登録するのはなぜですか。**

A. 本物の値をリポジトリに入れず、見本だけを共有するという Day 03 の線引きを、公開先でもそのまま守るためです。GitHub に置くと、リポジトリを見られる相手へ接続先ごと渡すことになります。Vercel の Environment Variables は公開されないので、本物はそちらだけに置きます。
