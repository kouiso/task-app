# 📝 レビュワーの意識すること

## 💬 コメントする上で意識すること

> **👍 いいと思った実装があればコメントする**
>
> **💡 他に良い書き方があれば suggest する**
>
> **[MUST][NITS][IMO][Q]のような項目を付ける**
>
> - NITS → 細かいかもしれないけど
> - IMO → 私はこう思うが、相手はどうかと尋ねる
> - Q → 質問
> - MUST → これは変えた方がいい
>
> **📝 レビュアが Resolve Conversation を消す**

## 🔍 レビューする観点で意識すること

### 🌟 共通

- ～Deprecated メソッド内で～Deprecated でないメソッドがコールされていないか
- そもそも～Deprecated のないメソッドも存在するため、全てが該当するとは限らない。ただし～Deprecated のついていないものが呼ばれていたら、まず怪しむとよい
- 変数名、関数名、カラム名等の命名が適切か(typo 含め)
- 用途に即しているか。
- 否定名は避ける。
- 関数→動詞、変数→名詞、temp みたいな意味のない文字を使っていないか。
- 冗長なコーディングになっていないか
- nest が深すぎないか。 → Linter でチェック(例：3個あれば警告、5個でエラー出すようにする)
- 凝縮度が適当か。単一責任の原則に即しているか。
- 逆に分割されすぎていないか。
- 各レイヤーのふさわしい場所にコードが記載されているか。
- 使われていないコード（デッドコード）が存在していないか。Linter でチェックできる。参照されていない関数の検出は、ライブラリやスクリプトで対応できる場合がある
- スコープの範囲
- 受入条件が満たされているか→やったことを受入条件に変更する
- 動作確認まではしない
- 自分が以前経験した落とし穴系にはまってないか
- ビジネスロジックがちゃんと適用されているか。（とくに権限周りで、閲覧や操作が許可されていない人に見えてしまっていないか。）
- 意図しない動作をしたときに検知できる仕組みがあるか
- 捨てやすいコードか（関数や役割ごとのファイルへ切り分けられているか）
- 再利用しやすいコードであるか。
- js の書き方として誤りがないか。より変更に強い書き方かどうか。
- パフォーマンス上問題はないか
- 処理のハンドリングが正しく行えているか
- 例外処理が書けているか
- 意図しない動作をしたときに検知できる仕組みがあるか
- 同期・非同期処理が書けているか
- 破壊的な変更をしていないか。
- エラーメッセージが適切で分かりやすいか

### 🎨 フロントエンド

- useState を無駄に作りすぎていないか
  - 例：1つの state で事足りるのにその state で別の state を作っている
- 親ではなく子コンポーネントで宣言すべき state がないか
- HookForm で不要な state が watch されていないか
- isDirty 使っていないか
  - isDirty の使用は、useForm に沿わない書き方を示すケースが多いため
- deps の設定が適切か
- useEffect や useCallback の ReRun 処理が正しいタイミングで書き変わっているか。
- コンポーネントの切り方が適切か
- デザインシステムに則ってかけているか(命名含む)
- デザインを再現できているか

### 🤔 悩むところ

- 書き方が人によって異なる場合がある。これをレビュー観点に入れるかは、レビュアーが違和感を覚えたら意図を聞いてフィードバックする方針とする
