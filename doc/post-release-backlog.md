## 1. コードの実務水準レビュー（直さない・報告のみ）

対象は `src/`（144ファイル / 15,926行）と `scripts/_*`（73ファイル）。
観点は「動くけど実務ではこう書かん」。認証・権限・SQL・入力検証を重点に見た。

**なぜ今やらんでええか**: 売っているのは教材の文章と画面であって、このアプリ単体ではない。
下の指摘はどれも「読者が写経して動かない」を起こさない。

### 先に良かったところ（直す必要が無いことの根拠）

- SQL は `Prisma.sql` のタグ付きテンプレートのみ。`$queryRawUnsafe` は
  `src/test/setup.ts` のテスト用 TRUNCATE だけで、本番経路に無い
- `as any` / `: any` / `@ts-ignore` / 空 `catch` / `console.log` は `src/` に **0件**
- 権限判定は `_helpers/permission.ts` に集約され、検索でも
  「メンバーシップ条件と caller 指定の projectId を AND で重ねる」形になっている（IDOR を潰す正しい形）
- ログイン rate limit は email / email×IP / IP の3軸 ＋ PostgreSQL advisory lock で、
  並行リクエストの取りこぼしまで塞いである

### 指摘 13件

重大度は「実務のレビューで MUST が付くか」で付けた。

#### HIGH

**H1. セッションを失効させる手段が無い（`src/lib/session.ts`）**
JWT を7日で発行し、失効リストもセッションテーブルも無い。`logout` は
`cookieStore.delete()` でクッキーを消すだけなので、トークンを一度でも
持ち出されたら**ログアウトしても7日間有効**。`user.changePassword`
（`src/server/api/routers/user.ts:224`）もパスワードを差し替えるだけで、
既存セッションを切らない。実務では jti ＋ セッション表で失効させるか、
アクセストークンを15分程度にして refresh を回す。
*緩和材料*: `trpc.ts` の `isAuthenticated` が毎回 DB を引いて `isActive` と `role` を
見直しているので、「アカウント無効化」と「権限降格」だけは即時に効く。

**H2. 全ユーザーのメールアドレスを列挙できる（`src/server/api/routers/project.ts:152`）**
`getAvailableUsers` は `canManageMembers` を持つメンバーに対し、
`isActive: true` な**システム全体のユーザー**を `USER_SELECT`（id/name/**email**/avatar）で返す。
プロジェクトを1つ作れば誰でもこの権限を取れるので、実質「登録者名簿が誰でも引ける」。
実務では、招待はメール完全一致の検索で1件だけ返すか、組織スコープで絞る。
なお教材（day12:219）は「この候補一覧には社内ユーザーの名前とメールアドレスが
並ぶため、メンバーを管理できる人以外には返しません」と書いて権限の門を説明している。
読者が理由を知らずに写しているわけではない。直すのはアプリ側の設計であって、
教材の説明を差し替える話ではない。

**H3. `SKIP_ENV_VALIDATION=true` が JWT_SECRET の長さ検証ごと外れる（`src/lib/env.ts`）**
通常経路の `envSchema` は `JWT_SECRET` に `.min(32)` を課しているが、
`buildFallbackEnv()` は「空かどうか」しか見ない。ビルド用に立てたフラグが
runtime に残ると、1文字の秘密鍵でも HS256 の署名が通る。
実務では、抜け道は「未設定を許す」までにして、**長さ・強度の検証は必ず残す**。

**H4. メールアドレスの変更に再認証も確認メールも無い（`src/server/api/routers/user.ts:177`）**
`updateProfile` は現行パスワードの再確認なしにメールを書き換え、その場で
新しいセッションを発行し直す。セッションを一度奪われた時点で
アカウントを完全に持って行かれる。実務では現行パスワード必須＋新アドレスへの確認リンク。

**H5. `register` に rate limit も列挙対策も無い（`src/server/api/routers/auth.ts`）**
`login` には3軸の制限があるのに、`register` は素通し。しかも既登録メールには
`CONFLICT`「このメールアドレスは既に登録されています」を返すので、
**登録済みメールを総当たりで判定できる**。実務では登録・パスワード再設定にも同じ枠をかけ、
応答は成否を区別しない文面に寄せる。

#### MEDIUM

**M1. Cookie の `secure` がテスト用の環境変数に依存（`src/lib/session.ts`）**
`secure: NODE_ENV === 'production' && process.env['PLAYWRIGHT_TEST'] !== '1'`。
テスト用の分岐が本番の判定式そのものに入っている。`PLAYWRIGHT_TEST=1` が
本番に紛れると Secure 属性が落ちる。実務では本番ビルドから分岐ごと消す。

**M2. `x-forwarded-for` の先頭を無条件に信頼（`src/lib/rate-limit.ts`）**
`extractClientIp` は先頭要素をそのまま client IP にする。ヘッダを自由に付けられる経路が
1つでもあると IP 軸の制限を回避できる。コメントに「Spoofing 対策はインフラ側で行う前提」と
書いてあるのは良いが、実務では信頼する proxy 段数を決めて**末尾から**数える。

**M3. 管理者のロックアウトを止めるガードが無い（`src/server/api/routers/user.ts:132`）**
`user.update` は ADMIN が自分自身の `isActive` を `false` にでき、
最後の ADMIN を `USER` に降格することもできる。実務では「最後の管理者」を守る不変条件を置く。

**M4. ログインのホットパスにテーブル全走査が乗る（`src/lib/rate-limit.ts`）**
`checkLoginRateLimit` は advisory lock を取ったトランザクションの中で
`loginAttempt.deleteMany({ createdAt: { lt: 30日前 } })` を毎回走らせる。
lazy cleanup をロック区間に入れると、行が増えるほどログイン全体が詰まる。
実務では cron / 定期ジョブに分ける。

#### LOW

**L1.** `decrypt` の `catch` が `console.error('Failed to decrypt token')` だけで例外本体を捨てる
（`src/lib/session.ts`）。期限切れと改ざんが区別できず、運用で原因が追えない。

**L2.** 観測経路が二本ある。tRPC とミドルウェアは `writeStructuredLog` を通すのに、
`auth.ts` / `session.ts` は `console.error` を直に呼ぶ。構造化ログ側にしか出ない事象と
標準エラーにしか出ない事象が混ざる。

**L3.** `updateProfile` のメール重複チェックが `findFirst` → `update` の 2 段で、
競合すると両方が通り得る。DB の unique 制約頼みになっている（P2002 を握る経路が無い）。

**L4.** `src/` と `scripts/_*/` に **73ファイル**の複製がある。現時点では
`src/lib/rate-limit.ts` も `src/server/api/routers/task.ts` も差分ゼロで揃っているが、
二重管理なので片方だけ直すと静かにズレる。同期を検査で縛るか、生成に寄せたい。

## 2. pre-commit の O(n²)

`lint-staged.config.js` の Gate 2 が、ステージした `dayXX_*.md` **1本ごとに**
`check_quality.sh` を呼ぶ。`check_quality.sh` はファイル単位の8検査に加えて、
毎回**自己テスト27本と corpus 全体15検査**を丸ごと走らせる。
つまり n 本コミットすると自己テストと corpus 検査が n 回走る。**1コミットあたり1回でいい。**

実測（この環境）:

| 対象 | 実測 |
|---|---|
| 1ファイル | 4.1 秒 |
| 3ファイル（逐次） | 12.3 秒 |
| 31ファイル換算 | **約2分7秒** |

直し方は、`check_quality.sh` にファイル単位の検査だけを回すモードを足し、
自己テストと corpus 検査は lint-staged 側で1回だけ呼ぶ形にする。

**なぜ今やらんでええか**: 遅いだけで、出る成果物は1回でも n 回でも同じ。
「1時間近くかかる」という当初の見立ては、この環境では再現していない（実測2分台）。
体感が違うなら、遅いのは別の要因（textlint や TypeScript 側）なので先にそちらを測る。

## 10. ダッシュボードに集計を出す章が無い

## 11. トップページ（`src/app/page.tsx`）が読者と製品で別物のまま終わる

Day 01 の写真を撮り直して1枚ずつ見たときに見つけた。

Day 01 は `src/app/page.tsx` に、見出し・3つのボタン・3枚のカードを並べた
着地ページを写経させる。`filepath: src/app/page.tsx` を含むブロックを全36本で
数えると、**このファイルを書くのは Day 01 だけ**で、後の日で置き換える章は無い。

一方、このリポジトリの `src/app/page.tsx` は次のとおりで、空行を除くと10行しかない。

```typescript
const session = await getSession();
if (!session) redirect('/login');
redirect('/dashboard');
```

読者の `/` は着地ページのまま、製品の `/` はログイン状態で振り分けるだけ。
この1画面だけ姿が違う。

今やらない理由は2つ。

- 読者の `/` には「ダッシュボードへ入る」ボタンがあるので、Day 07 でログインを
  足したあとも行き止まりにはならない。**進めなくなる読者はいない**
- 着地ページは Day 01 の教材上の役割（JSX と token を初めて書く場）を持っている。
  redirect に置き換えると Day 01 から書くものが無くなる

直すときは Day 07（ログイン）か Day 08（サイドバー）の終わりに

### 併せて直したい小さいもの

Day 01 のトップページを実画面で撮ると、左カラムの3枚のカードが狭く、
「プロジェクト」が「プロジェ / クト」と語の途中で折り返す。ボタンのラベルも
3つとも2行になる。読者の画面もこうなるので写真としては正しいが、
カードの最小幅か文字サイズを詰めれば読みやすくなる。
