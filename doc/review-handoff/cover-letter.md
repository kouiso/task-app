## 5. 直した本物の欠陥のうち、特に重いもの

### 5-1. コードがページの境で切れとった（局長の指摘が起点）

day13 p12 で `taskRouter` の宣言が `.input(` の途中で切れ、続きが次ページに落ちていました。
**写経が前提の教材で、読者は打ちながら紙をめくることになります。**

`book.css` の `pre` に `break-inside: avoid` を入れ、塊ごと次ページへ送るようにしました。
1ページに収まらん長さの塊は CSS の規定どおり分割されるので、コードが消えることはありません。
境に1〜2行だけ残る形も `orphans / widows: 4` で防いでいます。

代償はページ数です。36冊の合計で 2,600 → 2,879ページ（+279 / +10.7%）。
塊を丸ごと次ページへ送る以上ページは増えるので、増えたこと自体は想定どおりです。
増えた分と引き換えに何が良くなったかは紙面検査で測っており、
**36冊すべてで紙面の指摘が 0 件**、前より崩れた冊は 1 冊もありません。

**二度と戻らんように機械で見張る仕組みも足しました。**版面の下端に厚みのある濃い地色があり、
次ページの上端も同じなら「コードブロックがページの境で切れている」と報告します。
表の罫線1本を拾わんよう厚みの条件つきです。

### 5-2. 表の中のファイルパスが隣の列へ突き抜けとった

**既存の `check_pdf_book.py` は、この状態の day26 を「✅ 商品として出せる状態です」と

### 5-7. 読者が写経するアプリの文言がAI臭かった（局長の指摘が起点）

局長がスマホで Day 02 の画面を見て「アプリの中の文言がAI臭すぎる」と挙げてきた。
現物はこう出ていた。

```
ここで増えた価値
画面の主役が明確になって、次にタスク数やプロジェクト情報を足す余地も見えやすくなった。

次につながる視点
Day 03 ではこの変化を失わないように、ちゃんと履歴として残していく段階へ進む。
```

**これは解説文ではなく、読者が写経するコードの中身です。**買った人は自分のアプリへ
この文言をそのまま打ち込むことになる。教材の地の文なら読み流せるが、
成果物に焼き付く文言なので、質がそのまま商品の質になる。

数えた結果、症状は **day01・day02・day08 の3日に集中**していた。
day09 以降は一覧・フォームの普通のラベルで、この症状は出ていない。
（数え方: 教材の全コードブロックを `iter_blocks` で取り出し、実体の無い語
「温度感・空気感・芯・主役・余地・狙い・意識して進める・ワンフレーズ」等を数えた。母集団は30日ぶんの
コードブロック全数。）

`material-writing` の6手順に沿って、実体の無い語を落として具体へ書き直した。

| 前 | 後 |
|---|---|
| ここで増えた価値 / 画面の主役が明確になって、次に…足す余地も見えやすくなった。 | まだ無いもの / タスクの件数とプロジェクト一覧。Day 09 以降でここへ足す。 |
| 次につながる視点 / Day 03 ではこの変化を失わないように、ちゃんと履歴として… | 明日やること / Day 03 で、ここまで書いたコードを GitHub に保存する。 |
| 今日のワンフレーズ・今日のひとこと | メモ |
| todayGoal「教材の見本ではなく、自分の画面として立つ一枚にする」 | 名前と今日やることを画面に出す |
| role「Builder of Task App」 | タスク管理アプリを作る人 |
| まだ機能は少ないけど、見た目の温度感はもうプロダクトに寄せていく。 | 機能はまだ無い。色と余白だけ先に決めておく。 |

あわせて、JSX で「。」だけが行に独立していた箇所を次の文へ寄せた。
JSX は行間の改行を空白1つに畳むため、あのままだと句点の前に隙間が出る。
局長のスクリーンショットに写っていた「進める。 ただ文字を」の隙間がこれです。

書き直したあと検査を回しました。textlint は 0 件です。
教材側の検査も次の7本すべてが通りました。

- `check_tag_balance` / `check_why` / `check_tone`
- `check_terms` / `check_comprehension`
- `check_visualization` / `check_ja_line_break`

画面に出る文字が変わったので、day01・day02・day08 の写真7枚は撮り直しに回しました。

### 5-8. 画像の指定が効かず、写真が版面からはみ出しとった

`book.css` の PNG 向け指定は、幅を本文いっぱい、高さを 150mm までとしています。
ところが13箇所でその指定が**まったく効いていませんでした**。

原因は markdown の書き方です。`![...](....png)` の行の**すぐ上か、すぐ下に文章があると**、
CommonMark はその画像を文章の一部として扱います。すると HTML の `<figure>` にならず、
`figure img` を対象にした CSS が届きません。空行1つの有無で決まります。

結果として day02 の写真2枚は本文の幅を **13mm はみ出して**いました。
day01・day02 の最初の写真もこの状態でした。

空行を入れて直したあと、同じ写真を測り直した実測です。

| ページ | 前 | 後 |
|---|---|---|
| day02 p32 | 166.2 × 158.0mm | 152.6 × 145.1mm |
| day02 p4 / p5 | 幅 165.9mm（本文の幅は 152.4mm） | 幅 152.4mm |

12箇所が「画像の下に文章」、1箇所（day04）が「画像の上に文章」でした。
最初は下だけを探していて day04 を取りこぼしたので、上下の両方で30日ぶんを数え直しています。

この欠陥は CI が赤くなって初めて表に出ました。目視だけでは出なかった種類です。
