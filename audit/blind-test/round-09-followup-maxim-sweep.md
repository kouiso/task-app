# 第9回の残作業（1）: 「一般化した教訓で締める」形が他に残っているかの走査

第9回が出した作業のうち、「その形が他の段落に残っていないかを探す」に対する結果である。
書き直しは行っていない。**探した結果だけ**を記録する。

## 探し方

第7回で判定者が当てた特徴は「リスクの提示から教訓への締めが完成形の型で、
余分な引っかかりが一切ない」だった。その「締め」の部分だけを機械で拾う。

対象は `material/30days-curriculum/day*.md` の30ファイル。コードの囲いの中と、
見出し・箇条書き・表・引用の行は除く。**段落の最終文**（次の行が空行である文）が
次のいずれかで終わるものを数えた。

```text
のが基本です。/ が大切です。/ が原則です。/ という考え方です。/ を心がけます。
覚えておきましょう。/ のが定石です。/ べきです。/ が望ましいです。
習慣にしましょう。/ 癖をつけましょう。
```

## 1回目の走査は使えなかった

最初は「〜しましょう。」を含む広い形で数えて56件が出た。中身を見ると、
大半は「いま、これをやってください」という**手順の指示**だった。

- `day01:389` 「土台ができたら、一度開発サーバーを起動して、ブラウザで画面を確認しましょう。」
- `day02:729` 「ブラウザで見直しましょう。」

これらは読者に次の行動を渡す文であって、抽象的な教訓ではない。同じ語尾でも
役割が違うので、数えても判定の材料にならない。語彙を「抽象的な教訓」に絞り直した。

## 結果: 5件

| 場所 | 締めの文（末尾） |
|---|---|
| `day01_開発環境を整えて、初めてのアプリを動かそう.md:857` | アプリ内のページ移動には `Link` を使うのが基本です。 |
| `day03_GitHubに保存する.md:309` | ignore 設定があることと、送信前に自分でも `git status` で確認することの両方が大切です。 |
| `day10_プロジェクト新規作成.md:969` | tRPCでは `mutation` の成功時に `invalidate()` を呼ぶ、この形を覚えておきましょう。 |
| `day25_プロフィール編集.md:720` | 押してほしい順に濃さを変える、という考え方です。 |
| `day30_完成版を公開！.md:1002` | 学び続けること、作り続けることが大切です。 |

30ファイル中5件で、1ファイルあたり0.17件である。第7回で当てられた段落と同じ形は、
教材全体に広がってはいない。

## 書き直していない理由

`audit/cross-day-consistency.md` に残っている7周の記録は、**直すたびに新しい文が入り、
その新しい文へ誤りが混ざる**ことを示している。5周続けて、見つかった欠陥の全部が
前の周の修正そのものだった。

この5件は機械の判定を持たない。直した結果が良くなったかどうかを測る手段が、
書いた本人の感想以外に無い。したがって、ここで直すと「直した→たぶん良くなった」を
積み上げるだけになる。

先に必要なのは第9回が挙げたもう1つの作業、**書き直し版を混ぜ物と一緒に出して
単独で判定させる**ことである。それが通って初めて、この5件へ同じ書き直しを
当てる根拠ができる。

## この記録から出た作業

- 第10回: 第9回の書き直し版を、混ぜ物と一緒に出す形で単独判定にかける
- 第10回が通ったら、上の5件へ同じ書き直しを当てて、再度単独判定にかける
