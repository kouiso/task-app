## テスト仕様書の未実施項目との対応

`doc/test-spec-pr285-followup.md` が「本番未検証」としていた高優先2件について、
API層の自動テストで代わりになるものがあるかを1件ずつ突き合わせました。
結果として、代わりになったのは1件だけです。

| 仕様書の項目 | 突き合わせたテスト | 判定 |
|---|---|---|
| TC-01 1-3（削除済みタスクへの更新で CONFLICT） | `存在しないタスクは NOT_FOUND`（task.test.ts:183） | 未検証 |
| TC-01 1-4（`expectedUpdatedAt` 無しで無条件に更新できる） | `MEMBERはタスクを更新できる`（task.test.ts:151） | 検証済み |
| TC-02 2-1・2-2・2-3（移動先の position が最大値+1 になる ほか） | `同じプロジェクトへ同時移動しても position が重複しない`（task.test.ts:190） | 未検証 |

未検証と判定した理由は次のとおりです。

TC-01 1-3 は、削除済みのタスクへ `expectedUpdatedAt` 付きで更新をかけたとき、Prisma の
`P2025` を拾って CONFLICT になることを確かめる項目です。突き合わせたテストは
`expectedUpdatedAt` を渡していません。`src/server/api/routers/task.ts:293` の
`findTaskWithPermission` が先に走り、`src/server/api/routers/_helpers/permission.ts:65-70`
で NOT_FOUND を投げて終わります。CONFLICT に変換する経路（同 `task.ts:396-404`）までは
届いていません。

TC-02 は、移動先プロジェクトの最大 `position` + 1 が入ること（2-1）、移動先が空なら 0 に
なること（2-2）、担当者が移動先のメンバーでなければ外れること（2-3）を見る項目です。
突き合わせたテストが確かめているのは、同時に2件動かしたときに `position` が重複しない
ことだけです（task.test.ts:201）。値そのものも、担当者の扱いも見ていません。

検証済みと判定した TC-01 1-4 についても、経路は仕様書の想定と違います。仕様書は画面から
操作する手順を想定しており、ここで通したのはテスト用DBに対する呼び出しです。

なお、`楽観ロック: 古い expectedUpdatedAt では競合エラー`（task.test.ts:174）は、
古い `expectedUpdatedAt` を渡す TC-01 1-2 に当たるテストです。1-2 は仕様書で
本番実測済みの扱いになっており、未実施項目ではありません。
