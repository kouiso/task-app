### このリポジトリのゲートのコマンド

```bash
npx textlint material/30days-curriculum/dayXX_xxx.md
bash scripts/curriculum-qa/check_quality.sh material/30days-curriculum/dayXX_xxx.md
python3 scripts/curriculum-qa/run_writing_lint.py material/30days-curriculum/
```

`check_quality.sh` は渡されたファイルの置き場を corpus とみなし、`run_writing_lint` も corpus 検査の1つとして走らせる。
lint-staged が git commit 時に textlint と check_quality を実行する。

### textlint ルールの採否（task-app で 2026-07-15 に実測）

再検討する前にこの記録を読むこと。

| ルール | 実測結果 | 判定 |
|---|---|---|
| `ja-no-orthographic-variants` | 14件中5件(36%)が誤検知。「もの」と「者」を読みで同一視する。従うと意味が壊れる | 入れない |
| `textlint-rule-prh` + 辞書 | 教材に表記ゆれは無かった。prh は辞書の語しか捕まえず、漢字誤変換も拾えない | 入れない |

`ja-no-weak-phrase` が拾った文の例:


誤字脱字に安全な機械的解決は無い（上の3つで確かめた）。人間か LLM のレビューで拾う。

## 恒久ルール: 教材は実コードを編集しながら、その場で書く

1 Step は「作業ツリーの実コードを1か所変える → 動かして確かめる → その差分と理由を Step に書く」で1単位とする。
教材に載せるコードは作業ツリーの実ファイルから写し、手で打ち直さない。
後からまとめて書くことも、先に教材を書いてからコードを合わせることも禁止する。

このルールがある理由: 手で打ち直したコードは、どこかで1字ずれる。ずれたコードを写経した読者は、
教材のとおりに打ったのに動かない状態で止まる。読者には教材とコードのどちらが間違っているか判断できない。

教材の正解は、リポジトリの値の「正本のコード」にある。教材とコードが食い違ったら、教材を直す前に
「コードの書き方が初心者に教えられるか」を確かめる。教えられないならコードを先に直し、テストを通してから教材に写す。

## 優先関係

ルール同士がぶつかったときは、上の行を採る。

| 順位 | ルール | 例 |
|---|---|---|
| 1 | 恒久ルール（実コードから写す） | 説明が書きにくくても、コードを教材の都合で書き換えない |
| 2 | 教材固有の要請（手順を省かない・なぜを書く） | ブログなら削る冗長さも、手順なら残す |
| 3 | 定型句は0回（指紋・B-7 の上限0の句） | 「を可能にします」は1回でも直す |
| 4 | 構文の技法（対比・三連・「つまり」）は密度の上限内で使う | 取り違えやすい2つを区別する対比は残す |
| 5 | 文体の好み（語尾の揺らし方など） | 書き手の判断 |

`material/**` では material-writing が唯一の権威。`article-writing` や外部の技術ライティング原則は、
後述の一致点だけを借りる。衝突したら material-writing を採る。

## 書く前に必ず通す思考プロセス（guide 04 の6手順）

<!-- Source: hana652/tech-writing-pack guide 04 — Collocation. CC BY 4.0. -->

この6手順は「書き始める前」と「書き直す前」の両方で実行する。
linter は語彙の選択ミスを検出できない。判定できるのは書き手だけ。

### 手順 1 — 偏愛語を疑う

以下の語が文に登場したら、いったん手を止める。

| カテゴリ | 典型的な偏愛語 |
|---|---|
| 動詞系 | 落ちる・壊れる・刺さる・効く・回る・動く・走る |
| 名詞系 | 設計・仕組み・構造・本質・流れ・全体像 |
| 形容詞・副詞系 | 解像度が高い・手触り・深い・シンプルな・綺麗な |

「設計」「構造」はコーディング教材で正当に使える語だが、抽象的な概念（情報・理解）に被せると擦り倒しになる。

### 手順 2 — 対象に実体があるか判定する

| 実体あり（OK） | 実体なし（擦り倒しの疑い） |
|---|---|
| 「DBスキーマ設計」→ 実際のテーブル定義がある | 「情報設計」→ 何の情報？どのテーブル？ |
| 「サーバーが落ちる」→ プロセス終了が実体 | 「体験が壊れる」→ 何がどう変わる？ |
| 「画面が再描画される」→ 描画の処理が実体 | 「本質がわかる」→ どの動作が変わる？ |

判定ルール: 名詞の指示対象を1文で説明できるか。できなければ擦り倒し。

### 手順 3 — NGなら比喩に逃げず具体へ書き直す

```text
❌ 「この情報が落ちると設計が壊れる」
✅ 「ユーザー ID が空のままだと、DB へ渡す検索条件が組み立てられずエラーになる」
```

比喩でごまかさない（「まるで積み木が崩れるように…」）。具体の動作に翻訳する。

### 手順 4 — 構文の癖を直す

| 癖のある構文 | 直す方向 |
|---|---|
| 「〜は、〜だった」（過去形で語る） | 現在形 or 命令形へ（「〜になる」「〜してください」） |
| 「AではなくB」の対比が1文内に同居 | 2文に分ける。否定する A を読者が本当に思い込みそうか先に確かめる |
| 「〜という」の入れ子 | 「〜とは」で定義文に |
| 「〜のようなもの」 | 実体で定義する |
| 並列以外の読点（「〜は、」「〜が、」「〜ので、」の息継ぎ） | 読点は入れ替えても意味が変わらない並列の要素の間にだけ打つ。読みにくい文は2文に分けるか語順を変える |

### 手順 5 — 動詞・助詞・形容詞の選択ミスを正す

慣用句の破壊に注意（「課題を改善する」→「課題を解決する」「改善策を実施する」）。

| NG | OK |
|---|---|
| 「問題を改善する」 | 「問題を解決する」 |
| 「知識を身につける」（教材で頻出） | 「〜できるようになる」（行動目標に変換） |
| 「うまく動く」 | 「エラーなく起動し、〇〇を返す」 |
| 「ちゃんと設定する」 | 「.env に DATABASE_URL を記述する」 |

### 手順 6 — 重言・翻訳調を消す

| 重言 | 翻訳調（英語直訳臭） |
|---|---|
| 「まず最初に」→「まず」 | 「〜することができます」→「〜できます」 |
| 「約〜程度」→「約〜」 | 「〜という点に注意」→「〜に注意」 |
| 「返り値を返す」→「返す」 | 「行うことが必要です」→「必要です」 |

## レジスタ注意（教材と外部発信の違い）

- 教材の地の文は敬体（です・ます）で、軽い親しみを持たせる。AI 臭・翻訳調・偏愛語は排除する。
- global `ja-anti-ai-tone` は PR/Issue/Slack 等の外部発信文専用。教材 md には適用しない。

## 文体スペック

### 基調 — ですます体（関西弁ペルソナとの衝突に注意）

地の文（コードブロック・引用以外）はすべてですます体。Claude のペルソナは関西弁だが、教材本文には持ち込まない。ここが最も混入しやすい。

| 許可される語尾 | 禁止される語尾 |
|---|---|
| です / ます / ました / でした | だ / だぞ / だろ / しろ |
| しましょう / してみましょう | やで / やな / やねん / ちゃう |
| ですね / ますね | ワイ / からや / ええわけやない |
| ポイントです / 確認してみましょう | 命令形単体（「書け」「使え」「確認しろ」） |

| ❌ 実際に混入した例 | ✅ 直した形 |
|---|---|
| `初期セットアップは完了やで。` | `初期セットアップが完了しました。` |
| `サーバー側がまだないからや。` | `サーバー側がまだないためです。` |
| `最初の一枚目は、ただ映えればええわけやない。` | `最初の一枚目は、見栄えだけが目的ではありません。` |
| `ワイが書いたコードを見てみよか。` | `実際のコードを見てみましょう。` |

AI 人格名（内田祐貴）・一人称「ワイ」・人格設定の私的な例（音ゲー・阪神タイガース・馬術・ペットの名前など）・著者名（奥付以外）は、
`run_writing_lint.py` が FATAL にする。コードブロックの中も見る。奥付で許すのは著者名だけ。
リポジトリの値の「writing-lint のモード」が `warn` のリポジトリでは、FATAL も報告だけで失敗にはならない。

### 禁止カテゴリ — AI典型構文

| ❌ NG | ✅ OK |
|---|---|
| することができます | できます |
| これにより | だから / なので / よって |
| 〜と言えるでしょう | 〜です / 〜になります |
| 〜ではないでしょうか | 〜ですよね |
| いかがでしたでしょうか | （削除する） |
| ここでは〜について解説します | （削除して本文から始める） |
| さまざまな場面で | （削除するか具体例を書く） |
| 言うまでもありません / あらゆる観点から | （削除するか具体項目を列挙） |

### 禁止カテゴリ — 英語直訳調（外部レビューで指摘された「翻訳文感」はここ）

| ❌ NG | ✅ OK |
|---|---|
| 〜することは可能です | 〜できます |
| 〜について言及 | 〜について / 〜を紹介 |
| 〜を実施します | 〜します / 〜を行います |
| 〜に関しても同様です | 〜も同じです |
| 〜を可能にします | 〜できるようになります |

## 密度の考え方（guide 07・08）

<!-- Source: hana652/tech-writing-pack guides 07, 08. CC BY 4.0. -->

AI 文体の違和感は、誤用ではなく頻度で生じる（guide 07 法則1）。「AではなくB」も「〜するだけ」も単体では正しい日本語で、
人間も使う。AI はそれを人間の数倍の密度で使う。だから対策は禁止ではなく上限で、判定は「表現の有無」ではなく「密度の超過」で行う。

もう1つ覚えておく法則がある。ルールを守らせると、守り方そのものが型になる（法則5）。
上限ぴったりまで均等に使う、全節のリードを同じ述語で始める、といった新しい機械っぽさが出る。
だから「2回目以降は形を変える」を、上限と対で守る。

上流の上限は2,000〜5,000字のブログ1本を前提にしている。教材の1日は1万〜4万字あるので、記事あたりの絶対回数をそのまま当てると、
正当な対比だけで全本が超過する（B-1 は27本、B-2 は28本が超過した）。超過が常態になると誰も読まない警告になるため、
正当が大半のカウンタだけを文字数に比例させた。AI臭が大半のカウンタ（B-7・指紋・「ちゃんと」）は上流の上限のまま厳しく見る。

誤検知の原因は3つで、ラッパーの前処理で除いた。

1. 表の行・見出し・太字だけの行・画像 alt を地の文として数える。
2. 空行・コード・表をまたいで文をつなぎ、別段落の文末がそろっただけで三連と数える。
3. 文の途中で改行した断片を1文として文体混在を判定する。

上限を変えるときは、先にこの表に実測を足してから `run_writing_lint.py` の定数を変える。

### writing-lint の判定（ラッパー）

`writing-lint.py` は rc=1 を FATAL のときにしか返さない。rc で判定すると、DENSITY 超過が何件あっても合格になる。
そこで `scripts/curriculum-qa/run_writing_lint.py` が本体の関数を借り、出力を自分で判定する。

- FATAL（壊れた句読点・慣用句混交・禁止固有名詞）は1件でも失敗。
- 失敗にするのはリポジトリの値の「writing-lint のモード」が `gate` のとき（既定）。`--mode warn` では同じ内容を報告するが exit 0 で、何も止めない。
- DENSITY が上限を超えたら、そのカウンタのヒット全件に処置が要る。処置は処置記録（リポジトリの値）に
  `action: keep` と理由で書く。直したものは `action: fixed` で残す。
- 処置が当たるヒットが無くなった keep は stale として失敗。直した後に keep を残すと、次に同じ文を書いたとき黙って通るため。
- 禁止固有名詞のうち、リポジトリの事情で本文に出てよいもの（例: 対話台本の話者として出る著者名）は、処置記録と同じ `_meta/` の
  `writing-lint-config.json` に `{"allow_names": [{"id": "author", "reason": "…"}]}` と理由つきで書く。id は `persona`・`first-person`・`persona-private`・`author`。
  AI 人格名・一人称・人格設定の私的な例は、教材に出る理由が無いので外さない。
- `--emit-pending <path>` で未処置のヒットを処置記録と同じ形で書き出せる。理由は1件ずつ書く。まとめて同じ理由を貼らない。

### ai-smell-lint は参考扱い（必須ではない）

`hana652-tech-writing-pack/scripts/ai-smell-lint.py` は、task-app の30本すべてで rc=1 になった（2026-10-30）。
主な原因は1日骨格に入っている定型句（「全体の地図」「ここまで見えていれば」）と、表の空欄の「—」。
ゲートにはせず、書き終えた Day の読み返しの参考に使う。新しく骨格を作るときは、この定型句を使わず、表の空欄は「なし」と書く。

## 5つの不在（思考の問題として理解する）

<!-- Source: hana652/tech-writing-pack guide 03 — Anti-AI 5 Absences. CC BY 4.0.
     以下は原文（ブログ記事向け）に忠実な要約。教材固有の要請は「教材レジスタでの読み替え」に分けて書く。 -->

5つの不在は「禁止表現のリスト」ではなく、思考の欠落を指す。表現を潰して回るのではなく、なぜその思考が生まれるかを理解する。

1. **態度の不在** — AI は全トピックを同じ温度で書く。人間は大事な所に力を入れ、どうでもいい所は流す。書く前に「このテーマのどこが重要か」を1行で言語化し、それを文章の温度にする。
2. **勇気の不在** — AI は「〜と言えるでしょう」で保険をかける。各セクションで「結局どうなのか」を最低1つ言い切る。断言できないときは条件を切って、それぞれ言い切る。
3. **省略の不在** — AI は聞かれていないことまで網羅しようとする。「ここを読み飛ばされても主旨は伝わるか」を試し、伝わるなら削る。
4. **リズムの不在** — AI の文章は文の長さが均一になる。長い文の後に短い文、長い段落の後に1文だけの段落、という緩急をつける。
5. **沈黙の不在** — AI はすべての段落に結論とまとめを書く。あえて結論を書かず、問いだけで段落を閉じることもある。

詳細と症状パターン①〜⑮は `hana652-tech-writing-pack/guides/03-anti-ai.md` を読む。

### 教材レジスタでの読み替え（hana652 の原則とは別の、教材固有の要請）

- **手順は省略しない**（3 とは逆方向）。「同様に」「残りも」「以下略」で手順を端折ると、初心者はコードを追えなくなる。
- **「なぜ」は明示的に書く**（5 とは逆方向）。初心者教材では「こう書きます」の後に必ず理由を添える。次節で扱う。

## なぜを教える — メンタルモデルを渡す（手順書化の禁止）

<!-- Source: Xamfonos/technical-writing-best-practices (MIT)。開発者向けのトーンは採らず、3原則の考え方だけを使う。 -->

「これを書け → 確認」の羅列は手順書であって教材ではない。コードブロックの後には必ず「なぜこう動くか」を書く。

1. **手続きの前に、その手続きが解く問題を示す。**（`xamfonos-technical-writing-best-practices/SKILL.md:137` Introduced Abstractions）「一覧を返す関数を書きます」ではなく「一覧画面は全件を取ってくる必要があります。その入口を1つ作ります」から入る。
2. **新しい概念は、読者が既に知っている論理構造に結びつける。**（同 `:205` Mental Model Anchoring）引数・戻り値が何を保証しているかを、暗記ではなく理屈で分かる形にする。
3. **段階的な洞察 — 一度に全部渡さない。**（同 `:225` Layered Insight）概念→仕組み→実装の順に層を分け、前の日の理解の上に積む。

判定基準: 読者がこの節を読んだあと、次の似た手続き（一覧の次の新規作成など）を自力で書ける見込みがあるか。
無ければ「なぜ」が足りない。手順を増やすのではなく理由を足す。

- [ ] 対象 Day の完成定義を1文で書いた（「Day X 終了時点で読者は〇〇ができる」）
- [ ] 前の Day で習得済みの前提知識をリストアップした
- [ ] 新出の専門用語を洗い出し、初出箇所に注釈（括弧書き）を入れた
- [ ] 載せるコードを、作業ツリーの実ファイルから写す準備ができている（恒久ルール）

## 執筆後のゲート（順番厳守。コマンドはリポジトリの値の節）

1. **Gate 1: 文章衛生（textlint）** — 既知パターンの書式・冗長表現・句読点・文長・である/ですます混在を見る。語り口と翻訳文感は保証しない。
2. **Gate 2: 品質（check_quality.sh）** — 視覚化・コードブロック長・ステップ連続性・禁止ワード・コード完全性・文体・理解度と、corpus 全体の検査（writing-lint を含む）。
3. **Gate 3: 冷えた読み手の通し読み** — 自分が書いた内容を知らない別のエージェントに、完全初心者として読ませる。

ゲートは「通ってから出す」ではなく「通るまで書き直す」。

### Gate 2 のコードブロック例外

コードブロックはリポジトリの値の行数以下が原則。読者が1ファイルとしてそのままコピーする必要があり、分割すると途中状態や
手作業の結合を生む場合だけ、対象フェンスの直前に次の印を置ける。

```markdown
<!-- code-block-length-exception: complete-copy-unit -->
```

例外ブロックには filepath 行が要る。上限以下のブロックへの例外、印だけを置くこと、印とフェンスの間に本文を挟むことは失敗になる。

### Gate 3 の実行プロンプト（別エージェントに渡す）

```text
あなたはプログラミング初心者です。
以下の条件を前提にこの教材を読んでください:
- （リポジトリの値の「Gate 3 の読み手像」をここに貼る）

教材の先頭から末尾まで確認した範囲を示し、以下を行番号付きで報告してください
（見つからなければ、確認した観点とともに「なし」と明記）:
1. 詰まりポイント（見つかった分を全て。「なぜ詰まるか」を具体的に）
2. 注釈なしで登場した専門用語（行番号と用語名）
3. 「次のStepに進んでいいか」確認できない箇所
4. 「ここで何をやっているか」がわからない箇所
5. エラーが出た時の対処法が書かれていない箇所
6. 偏愛語の擦り倒しが疑われる箇所（「〇〇行：『設計が壊れる』→実体が不明」の形式）

指摘数をレビュー成立の条件にしない。0件でも、全範囲と全観点を確認した根拠があれば成立する。
```

判定基準:

- 有効な詰まりポイントがある → 全て直して Gate 1 に戻る
- 詰まりポイントが0件 → 対象範囲と6観点の確認根拠を記録して成立。件数を作るための指摘は足さない
- 対象範囲または観点の確認根拠が無い → 不成立。プロンプトを見直して再実行
- 偏愛語の擦り倒しが1件でも挙がった → 6手順（手順1〜3）で書き直して Gate 1 に戻る

人間の初心者テストを行っていない場合は、未実施の制約として記録し、実施済みとは報告しない。
