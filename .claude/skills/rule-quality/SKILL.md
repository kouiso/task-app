# 品質・実装・作業ルール

このファイルは task-app 内 `prompt/instructions/quality.instructions.md` と
`prompt/instructions/testing.instructions.md` を統合したもの。Copilot向けの原本は
両ファイルとも変更していない。

## 1. Implementation Rules (実装ルール)

### 1.1. 基本方針

- **妥協禁止**: 最小の詳細にも鋭い目、常にベストプラクティス追求
- **既存コード尊重**: スタイル・設計思想を完全模倣、逸脱時は提案→許可→実装
- **範囲外タスク**: 承認者の指示外作業は提案→許可取得必須
- **積極的調査**: WebSearch・Tavily積極活用、思い込み・推測禁止

### 1.2. リポジトリ調査

- **作業前必須**: 全ファイル・ディレクトリ・ドキュメント（リンク先含む）完全把握
- **質問制限**: ソースコード調査後の不明点のみ
- **不明点即調査**: 許可を求めずTavilyで即座調査（TypeScript、Biome、Prisma、NestJS等）

### 1.3. 基本記述ルール

1. **日本語記述必須**: ソースコード・コメント・ドキュメント全て
2. **コメント基準**: 実装理由説明のみ（「Why」のみ、「What」禁止）
3. **自明コード**: コメント追加回避
4. **複雑部分**: 意図・理由説明集中

### 1.4. 品質基準

- ベストプラクティス常時遵守
- 品質・セキュリティ妥協なし
- 幻覚・虚偽情報回避、事実ベース回答
- 承認者意図理解、期待を超える成果

### 1.5. 作業制限

- **テスト用ファイル作成禁止**: リポジトリ内作成厳禁
- **架空動作確認禁止**
- **他プロジェクト情報推測・記載完全禁止**: WebSearch・Tavily確認必須
- **コミットメッセージ他プロジェクト情報完全禁止**: 現プロジェクト変更内容のみ

### 1.6. 作業プロセス

#### 指示分析・計画
- 主要タスク要約、制約内技術確認
- 主要要件・潜在問題特定、具体ステップリストアップ
- 最適順序決定、必要ツール・リソース検討

#### タスク実行
- 各ステップ順次実行、完了時簡潔進捗提供
- 問題・質問即時報告、解決策提案
- **不明点・怪しい実装**: WebSearch・Tavily必須確認（許可不要、積極実行）

#### 品質管理
- 各タスク結果迅速検証、エラー・不整合即修正
- コマンド実行標準出力確認・共有
- **作業完了時**: テスト実行（テストコード存在時）
- **CI・formatコマンド必須実行**: 全エラー解消まで継続
- **エラー解決**: 諦めず根本解決（Biomeの診断も対象）

#### 最終確認
- 全タスク完了時成果物全体評価
- 元指示比較、必要時調整

### 1.7. 並行作業注意事項

1. ファイル・フォルダ操作エラー時（権限等）→ 他AI作業中判断
2. 作業中エリア回避、別モジュール・ディレクトリ移動継続
3. 作業開始前対象ディレクトリ操作可能確認
4. 競合回避、一度一モジュール・ディレクトリ作業完結
5. 他AI任せなし、他AI問題積極解決、ミスカバー振舞
6. **他AI競合回避**: ファイルロック時別タスク移行
7. **他AI問題**: 積極検知・解決協力

### 1.8. リファレンスリポジトリ活用

作業開始前参照リポジトリ構造詳細調査：
1. ディレクトリ構造・階層
2. ファイル命名規則・パターン
3. 設計パターン・配置方法
4. モジュール間依存関係管理方法
5. 確立設計パターン理解

### 1.9. リポジトリヘルスチェック（必須実行）

**定義**: `task init && npm run fix && npm run lint && npm run test`

**タスク完了後必須自主実行**:
- `task init`: Docker環境初期化、依存関係インストール、DB リセット・シーディング
- `npm run fix`: Biomeで自動修正
- `npm run lint`: Biomeでリントチェック
- `npm run test`: Vitest テストスイート実行

**全成功までタスク未完了。エラー発生時根本原因解決、全チェック通過必須。**

### 1.10. 作業時注意事項

**他AI編集中ファイル除外、以下厳密遵守**:

1. **構造・命名規則整理**: 機能変更不要時限定
2. **既存振舞変更回避**: デグレ絶対防止
3. **インポートパス修正**: 慎重実施
4. **設計パターン優先**: 参照元ディレクトリ構造・命名規則・モジュール分割・依存関係管理
5. **既存ファイル活用優先**: 新規作成より既存活用
6. **他AI作業領域回避**: 重複回避注意
7. **エラー解決**: 参照元設計パターン優先
8. **バックアップファイル**: 作成禁止、発見時削除
9. **未使用変数エラー**: アンダーバー禁止、削除解決
10. **テストコード**: 不存在箇所積極追加（本来タスク一部、独立タスク勝手追加禁止）
11. **指示外共通化**: 実施禁止
12. **追加指示**: copilot-instructions.md未記載時追記、指示者報告必須
13. **docker-compose.yml/Dockerfile存在**: `npm run build`直接実行禁止、`npm run lint`確認
14. **不明実装・エラー**: WebSearch・Tavily必須調査（許可不要、即座実行）
15. **他プロジェクト比較・参照**: 慎重実施、実際情報確認後記載
16. **段階的リファクタリング注意**:
    - 未使用型定義・関数即削除
    - 関数名変更時全参照箇所同時更新
    - 重複関数定義発見次第削除
    - 中間状態未使用コード・Biomeエラー残存禁止

### 1.11. その他技術規約

- **Taskfile**: 可能な限り`task`コマンド使用

### 1.12. 成果物URLの即時共有義務

**PR・Issue・ブランチ等を作成したら、完了報告と同時にURLを必ず共有すること。**
「PR作成しました」だけで終わり、ユーザーに聞かれてからURL提示するのは禁止。作成完了 → 即座にURL共有。

### 1.13. 作業ミス時の即座クリーンアップ義務

**間違えて作成したブランチ・ファイル・コミットは、ミスに気づいた時点で即座に削除・修正すること。**
ミスに気づいても放置して次の作業に進むのは禁止。ミス発覚 → 即座にクリーンアップ → 本来のタスクに戻る。

## 1.14. TDD & Testing Rules (TDD・テスト運用ルール)

**すべての実装はTDD (Test-Driven Development) で進めることを基本とする。**

### RED → GREEN → REFACTOR サイクル

1. **RED Phase**: 要件を明確にし、テストケース（正常系、異常系、エッジケース）を設計する。失敗するテストを書く。予想通りに失敗すること（RED）を確認する。
2. **GREEN Phase**: テストを通すための**最小限の実装**を行う。テストを実行し、通ること（GREEN）を確認する。
3. **REFACTOR Phase**: コードの重複を排除し、可読性を高める。テストを再実行し、GREENが維持されていることを確認する。カバレッジが80%以上であることを確認する。

```typescript
// AAAパターン（Arrange-Act-Assert）は必須
describe('UserService', () => {
  it('should create user with valid data', async () => {
    // Arrange (準備)
    const userData = { email: 'test@example.com', name: 'Test User' };

    // Act (実行)
    const result = await userService.createUser(userData);

    // Assert (検証)
    expect(result).toEqual(userData);
  });
});
```

テスト名は `should + 期待される振る舞い` の形式にする（❌ `it('test user', ...)` のような曖昧な名前は禁止）。

### テスト品質基準

1. **カバレッジ要件**: 最低80%のカバレッジ（Statement, Branch, Function, Line）を必須とする。重要部分（認証、決済等）は100%。
2. **AAAパターン**: Arrange (準備) -> Act (実行) -> Assert (検証) の構造を守る。
3. **エッジケース網羅**: 0除算、空配列、null/undefined、最大値/最小値などをテストする。
4. **適切なモック**: 外部依存（DB、API等）は適切にモック化し、テストの実行速度と安定性を確保する。ユニットテストで実際のDBアクセスはしない。
5. **テストの独立性**: 各テストケースは独立して実行可能であり、実行順序に依存しないこと。
6. **速度と信頼性**: 全テストは数秒で終わること。非決定的なテスト（flaky test）は排除する。
7. **保守性**: テストが壊れたら、まず実装側の問題を疑う。

### 実装時のチェックリスト

- [ ] テストを先に書いた（RED確認）
- [ ] 最小実装を行った（GREEN確認）
- [ ] リファクタリングを行った
- [ ] カバレッジ ≥ 80%
- [ ] エッジケース・エラーケースをテストした

## 2. Absolute Prohibitions (絶対禁止事項)

**ルール違反は即時タスク失敗。例外一切認めず。**

### 2.1. ファイル管理禁止事項

#### バックアップ/一時ファイル作成の完全禁止

**以下の全パターンを禁止**:
- 拡張子付きバックアップ: `.bak`, `.backup`, `.old`
- プレフィックス/サフィックス: `_backup`, `_temp`, `2`, `_copy`
- 作業用ファイル: `test.js`, `temp.ts`, `debug.ts`, `work.ts`
- 日付付きファイル: `backup_20240101.ts`

**発見時は即座に削除。動作確認は既存テストコード内で実施。**

### 2.2. コメント規約

- **禁止**: 「What」コメント（例: `// ユーザー取得`）
- **許可**: 「Why」コメント（実装理由の説明のみ）
- **禁止**: 英語コメント（`// TODO: implement this`） → 日本語で書く（`// TODO: この処理を実装する`）

### 2.3. コード品質禁止事項

- 未使用変数はアンダースコア（`_`）で回避せず、変数削除で解決する

### 2.4. Biome設定関連禁止事項

- **設定ファイル変更の完全禁止**: `biome.json`等の設定ファイルは明確な個別許可時のみ変更。ソースコード側での根本解決を優先。
- **無効化コメントの完全禁止**: `// biome-ignore`等は使わず、適切修正・web_search調査・アーキテクチャ見直しで対処。

### 2.5. 安易な回避策の完全禁止

#### 既存ロジック（特に状態初期化）の安易な削除禁止

UX改善（ちらつき防止等）のために、バグ修正として導入された既存の状態リセット処理（`state = []`等）を削除することを禁止する。過去のバグ（データの重複、不整合等）が再発する（デグレ）ため。ロジックは維持し、UI側（ローディング表示の条件分岐等）でUXを改善する。

#### 「ついでに改善」の完全禁止 (No Scope Creep Protocol)

**バグ修正・Issue対応時に、指示された範囲外の変更を勝手に含めることは重大な違反。**

「最小限の差分」と言われたら、**バグを直すために絶対必要な1行だけ**を変更する。「ついでにリファクタリング」「関連してるからAPI構造も変更」「パフォーマンス改善にもなるし」という思考は禁止。改善案は別途提案し、「ついでに」ではなく「別Issue/PRで対応しますか？」と確認する。

#### Git操作回避の禁止

- **`--no-verify`フラグの完全禁止**: `git commit --no-verify`、`git push --no-verify`は禁止。hookが指摘するエラーを全て修正する。提案すら重大な違反。
- **`git reset`コマンドの完全禁止**: `--hard`/`--soft`/`--mixed`全形態禁止。間違ったコミットは`git revert`で取り消す。コミットメッセージ修正は`git commit --amend`のみ（最新コミットのみ）。複数コミットの整理は`git rebase -i`のみ（ローカルブランチのみ）。
- **`npm install --legacy-peer-deps`の完全禁止**: peer dependenciesの不一致は根本的に解決する。

#### Biome エラーの完全解決義務

作業範囲外のファイルでもBiomeエラー発見時は必ず修正する。「このファイルは触っていないので」という理由での放置は禁止。エラーが100件、1000件あっても全て修正する。「エラーが多すぎるので設定を緩和しましょう」という提案は禁止。

#### 安易な代替案提案の禁止

以下のような**手間を避ける提案**は完全禁止：

❌ 「エラーが多いので、一旦`--no-verify`でコミットしましょう」
❌ 「このファイルは作業範囲外なので、エラーは無視しましょう」
❌ 「時間がかかるので、別の簡単な方法にしませんか」
❌ 「とりあえず動くので、リファクタリングは後回しにしましょう」
❌ 「テストが多すぎるので、一部だけ実行しましょう」

### 2.6. GitHub書き込み操作の禁止

**ユーザーから明確な指示があるまで、以下のGitHub書き込み操作は完全に禁止する。**

- 禁止対象: PRレビューコメントの投稿、Issueコメントの投稿、PR/Issueの作成・更新、ラベルの追加・削除、アサイン操作
- 許可される操作（読み取り専用）: PR/Issueの内容確認、コードの差分確認、レビューコメントの閲覧、リポジトリ情報の取得
- 正しい手順: レビュー内容やコメント案をユーザーに提示 → 明確な投稿許可を得る → 投稿を実行

### 2.7. 完全動作検証の絶対義務 (End-to-End Verification Protocol)

**自分の目で見て確認したもの以外は、絶対に成功と報告するな。推測・想像・希望的観測は即座にタスク失敗とみなす。**

#### 作業開始前の必須調査（Phase 0）

**いかなるタスクも、以下の完全調査なしに着手することは重大な違反行為である。**

1. **リポジトリ全体の完全把握**: 全ディレクトリ構造の把握、全ソースコード・設定ファイルの読込、全ドキュメント・マニュアルの熟読（README, doc/配下の.md全て）、コミット履歴・PR・Issueの確認
2. **ドキュメント優先の絶対原則**: `README.md`, `CONTRIBUTING.md`, `ARCHITECTURE.md`等の完全熟読、`doc`配下の全ファイル確認。**ドキュメントに書かれていることを無視した実装は、完全な職務放棄である**
3. **既存実装パターンの完全理解**: 類似機能の実装方法確認（Grep/Glob活用）、既存のテストコード・E2Eテストの確認、アーキテクチャ・設計パターンの把握

**上記を完了せずに作業着手した場合、即座にタスク失敗とみなす。**

「動作確認しました」という報告は、認証フローの完全実行・正常系の完全確認・実際のレスポンス確認・ログ確認・異常系確認・テストの完全実行の全てを実行した場合のみ許される。

禁止例:
- 「認証が必要ですが、認証なしで動作確認しました」
- 「コードを見る限り動くはずです」
- 「型が合っているので大丈夫なはずです」
- 「テストが通ったので本番も動くでしょう」

### 2.8. 実行中サービスの無断停止禁止

ユーザーが実行中のサービス（Metro、API、デバッガ等）を使用している時、AIが勝手に停止・再起動することは重大な違反。設定ファイルは修正してよいが、「次回起動時に有効になります」と伝え、再起動はユーザーに任せる。再起動が必要な場合は明示的に確認を取る。

## 3. Biome Rules (Biome設定に関するルール)

### 3.1. 基本規約

1. **Biome schema v2使用**: `biome.json`でv2スキーマを使用
2. **最新仕様理解**: 不明時web_search必須調査
3. **大元設定変更禁止**: 指示者別途指示なし勝手緩和・編集禁止、一時緩和設定指示者許可なし導入禁止
4. **ソースコード修正優先**: Biome設定変更でなくソースコード修正対応、大量エラー時指示者報告・対応方針指示、デグレ禁止

### 3.2. エラー対応基準

#### 積極解決条件（全満足時）
- 修正対象1ファイル内完結（他ファイル影響なし）
- 修正箇所10箇所以下
- 型定義追加・削除解決可能
- 単純構文書換対応可能（for文→map、var→const/let）

#### 一時設定緩和検討条件
- 修正複数ファイル跨り、影響範囲予測困難
- 大規模リファクタリング必要（関数分割・クラス設計変更等）
- 外部ライブラリ制約修正困難
- 修正既存動作変更リスク

### 3.3. 一時設定管理

作業中ファイル一時設定発見時は上記基準で削除可能判断し、削除可能判断時は必ず削除後コミットする。
